# Работа с BGIN

Сначала прочитай существующий документ через `bgin_read`, настройки через `bgin_settings` и каталог нужного типа через `bgin_catalog`. Новый документ или заготовку узла создавай через `bgin_create`. Изменения через `bgin_edit` возвращают новый документ в памяти; сохраняет его отдельный вызов `bgin_export`. Передавай источник как `{"path":"menu.json"}` или `{"document":{...}}`, с одним из двух полей.

Прочитай нужную справку, доступную также через `bgin_guide(topic=...)` и ресурсы `bgin://guide/{topic}`:

- [Формат JSON](references/json-format.md), тема `json-format`: при создании документа, изменении типов значений, спрайтов и анимации.
- [Объекты](references/objects.md), тема `objects`: назначение всех 31 типов, основные параметры и ограничения предварительного просмотра.
- [Композиция](references/design.md), тема `design`: при создании экрана или существенном изменении компоновки, с исполнимым примером JSON.

JSON — редактируемое дерево, а не дамп памяти. Не добавляй `type_hash`, `metadata_hex`, `sha256` или выдуманные свойства. Не удаляй непонятные сохранённые значения, явные типовые оболочки и повторные свойства. Схема кодирования, параметры загрузчика и степень воспроизведения в рендере отвечают на разные вопросы. Успешная сборка не доказывает игровой эффект поля. `Widget` и `GuiMgr` — классы движка, а не разрешённые JSON-типы.

Используй `bgin_search` для поиска пути узла. При проверке ветви передавай полный документ и `options.selected`, например `/screens/0/children/2`: отдельный вырезанный узел потеряет размеры родителей. `screen` — индекс с нуля. Размер предпросмотра и высота экрана влияют на процентные размеры текста и контейнеров.

Большой файл сначала осматривай через `bgin_read(include_document=false, depth=1)`, затем запрашивай нужный `pointer`. Для рендера можно передать `source.path` и путь выделения, не возвращая весь JSON в разговор.

Ресурсы внешние: `assetRoot`, `bginRoot`, `textureRoot`, `fontRoot`, явные псевдонимы `bindings`. Проверь их через `bgin_resource_report`. Ссылки `/Widgets/...` и `/Sprites/...` разрешаются через подключённые документы. Не заменяй отсутствующий ресурс случайной встроенной картинкой. Настройки можно сохранять через `bgin_settings`, а `options` и `resources` в запросе рендера переопределяют их для одного изображения. Относительные файловые пути считаются от папки конфигурации MCP.

Для сравнения вариантов вызывай `bgin_render` с 1–36 запросами. Изображения сгруппированы по девять; номера и координаты находятся в JSON ответа. Проверяй ошибки ресурсов и предупреждения, а не только картинку. `state`, `progress`, `page`, `frame`, `scrollX`, `scrollY` — настройки предварительного просмотра, не новые свойства BGIN. Предпросмотр не исполняет обработчики кнопок и не доказывает поведение событий в игре.

Композицию строй по обязанностям: общий экран, верхняя панель, основная область, нижние действия; внутри — отдельные группы подписей, значков и кнопок. HorizontalContainer и VerticalContainer распределяют соседей, StackContainer накладывает слои, MarginContainer задаёт отступы, AspectRatioContainer сохраняет пропорции. Один StackContainer со всеми элементами не заменяет структуру. Следуй визуальному образцу пользователя: одинаковые отступы, согласованные высоты кнопок, чёткая иерархия текста и небольшое число акцентных цветов. Используй существующие стили и спрайты только после проверки их наличия. Не придумывай обязательную палитру для всех экранов.

Перед экспортом вызови `bgin_validate`, сравни изменения через `bgin_compare` и проверь рендер при целевых разрешениях. `bgin_export` записывает отдельный файл; для BGIN требуется независимая проверка через `bgin_core`, доступный серверу по `--core-path` или `BGIN_CORE_PATH` (путь к родительскому каталогу `bgin_core`). Существующий файл назначения заменяется только с `overwrite`, с сохранением резервной копии. В результате различай проверку JSON, двоичного преобразования, изображения и испытание в игре.
